# Phase 1 – Kern: Modell, Befehle, Engine – Implementierungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ein vollständig getesteter, reiner Kern: das eine Datenmodell für Projekte und
Vorgänge (`plnwrk-core`) und die Engine (`plnwrk-engine`), über die jede Änderung als Befehl mit
Undo/Redo und Revisionsspur läuft, plus lesende Abfragen. Die CLI zeigt das Ergebnis als JSON.

**Architecture:** `core` hält Typen, Validierung und Invarianten (`Workspace::check`). `engine`
führt Befehle in einer Transaktion aus: Ein Befehl liest den Arbeitsbereich und schreibt nur über
`Tx::put/remove`; jede Schreiboperation wird als **umkehrbares Event** (`Put{before, after}`,
`Remove{before}`) festgehalten. Nach jedem Befehl prüft `Workspace::check` alle Invarianten; bei
Fehler oder Verstoß werden die Events rückwärts invertiert (Rollback). Erfolgreiche Befehle
werden als `Change` an ein Append-only-Log gehängt. Undo/Redo erzeugen neue, kompensierende
Changes; das Log wird nie umgeschrieben.

**Tech Stack:** serde/serde_json, ulid 3 (ohne std, mit serde), jiff 0.2 (nur `std`, `serde`),
thiserror 2, proptest 1, insta 1 (json), cargo-llvm-cov.

**Spec:** [docs/PLAN.md](../PLAN.md) §2, §3.2, §3.3, §7 Phase 1.

## Global Constraints

- core/engine: keine I/O, keine Uhr, kein Zufall (Reinheitsprüfung). Zeit über `Clock`, IDs über
  `IdSource` – beide als Traits in core, Implementierungen mit echter Uhr/echtem Zufall nur in Apps.
- Kein `unwrap`/`expect`/`panic!`/Indexzugriff in Produktionscode. Jede Eingabe ist feindlich.
- Datumswerte (Start, Frist, Meilenstein) sind `jiff::civil::Date` (Kalendertag, keine Uhrzeit);
  Zeitpunkte (erstellt, Änderung) sind `jiff::Timestamp` (UTC).
- Sammlungen sind `BTreeMap` nach ID → deterministische Reihenfolge in Ausgabe und Tests.
- Befehls-IDs `entity.verb` in Englisch; Parameter sind ein JSON-Objekt, **unbekannte Schlüssel
  werden abgelehnt**; bei Update-Befehlen bedeutet fehlender Schlüssel „unverändert“, `null`
  „leeren“.
- Textgrenzen: Titel 1–200 Zeichen (getrimmt, keine Steuerzeichen); Beschreibung/Kommentar ≤ 20 000
  Zeichen (Steuerzeichen außer `\n`, `\r`, `\t` verboten); Kurzlabels (kind, reference, role,
  initials, tag, email) ≤ 80 Zeichen, keine Steuerzeichen; max. 30 Tags je Aufgabe.
- Zahlengrenzen: progress 0–100; estimate_minutes 0–1 000 000; lag_days −365…365.
- Testabdeckung core+engine ≥ 90 % Zeilen (`cargo xtask ci` erzwingt es).

## Review Focus

1. **Zyklen über Umwege** (A→B→C→A bei Abhängigkeiten; Aufgabe unter eigenen Enkel hängen) →
   Befehl abgelehnt, Zustand unverändert (Tests in Task 3 und Task 8/9).
2. **Löschen mit Nachwirkungen** (Aufgabe mit Unteraufgaben, Abhängigkeiten, Kommentaren) →
   alles hängt mit dran weg, und ein einziges Undo stellt alles wieder her (Test in Task 8).
3. **Undo nach Zwischenschritten** (Undo, neuer Befehl, Redo) → Redo ist nach einem neuen Befehl
   nicht mehr möglich und meldet das sauber (Test in Task 5).
4. **Müll-Parameter** (falsche Typen, Riesenzahlen, fremde IDs, unbekannte Schlüssel, Nicht-Objekt)
   → nie Panik, Fehler benennt den Parameter, Zustand und Log unverändert (Task 12, alle Befehle).
5. **Vorlage ohne Startdatum oder mit Daten vor dem Start** → Instanziierung verschiebt Daten
   korrekt bzw. übernimmt sie ohne Daten, Vorlage bleibt unberührt (Test in Task 10).

  BadParam { param: String, reason: String }, NotFound(EntityKey), Invalid(Vec<Violation>), Conflict(String) }
pub struct Outcome { pub seq: u64, pub created: Vec<EntityKey> }
pub struct Session { … }
impl Session {

  pub fn with_workspace(ws: Workspace, log: Vec<Change>, clock, ids) -> Self; // für Phase 2
  pub fn workspace(&self) -> &Workspace; pub fn log(&self) -> &[Change];
  pub fn set_actor(&mut self, Option<PersonId>);

Ablauf `run`: Befehl finden (UnknownCommand) → `enabled` prüfen (Disabled) → Parameter-Schlüssel
gegen `spec.params` prüfen (BadParam für unbekannte/fehlende Pflichtparameter, Nicht-Objekt) →
`Runner::Edit(f)`: `Tx` auf dem echten Arbeitsbereich, `f(&mut tx, &params)`; danach
`ws.check()`; bei Fehler/Verstoß alle Events rückwärts invertieren → Fehler zurück. Bei Erfolg
ohne Events: kein Change, `Outcome{seq: letzte seq}`. Sonst Change anhängen, `undo`-Stapel +seq,
`redo`-Stapel leeren. `Runner::Undo`: oberste seq vom Undo-Stapel, inverse Events rückwärts
anwenden, neuer Change `command:"undo", undoes`, seq auf Redo-Stapel. `Runner::Redo`: analog
mit Original-Events, `redoes`, zurück auf Undo-Stapel (Redo-Stapel bleibt sonst erhalten).

  minimal `name`): Erfolg → 1 Change, Person da; `undo` → Person weg, Log hat 2 Changes, zweiter
  mit `undoes: Some(1)`; `redo` → Person wieder da; `undo, person.create, redo` →

  Params `[]` statt Objekt → `BadParam`; `Event::inverse` zweimal = Original;
  `Event::apply` mit falschem `before` → `Conflict`.
