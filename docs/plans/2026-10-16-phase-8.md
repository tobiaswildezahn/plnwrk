# Phase 8 – Veröffentlichung 0.1.0: Implementierungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** plnwrk 0.1.0 lässt sich ohne Rust installieren: Pakete für macOS, Windows und Linux
als GitHub-Release, die Browser-Version unter einer eigenen Subdomain, eine Kurzanleitung für
Menschen ohne Technikwissen.

**Entscheidungen (Tobi, 2026-10-16):**
- **Unsigniert** für 0.1.0. Die Kurzanleitung erklärt den ersten Start trotz Warnung
  (macOS ab 15: Datenschutz & Sicherheit → „Dennoch öffnen“; Windows: „Weitere Informationen →
  Trotzdem ausführen“).
- **Eigener Release-Ablauf** statt `cargo-dist` (Abweichung von PLAN §7 Phase 8):
  - Ein Tag `v0.1.0` baut alle drei Plattformen und veröffentlicht einen GitHub-Release.
  - Aktionen sind auf Commits festgelegt wie beim Pages-Ablauf.
  - Schreibrechte hat nur der letzte Schritt.
- **Browser-Version unter eigener Subdomain**, Vorschlag `plnwrk.wildezahn.de`. Tobi legt den
  DNS-Eintrag an; der Browser-Speicher wird dann mit keiner anderen Seite geteilt.
- **Doku:** nur eine deutsche Kurzanleitung (`docs/handbuch.md`). Keine `mdbook`-Doku und kein
  CONTRIBUTING; SECURITY.md und eine englische Fassung folgen später.

**Architecture:**
- **Version 0.1.0** im Workspace-`Cargo.toml`. Sie erscheint in der App (Startseite), in der
  CLI (`--version`), beim MCP-Server (`serverInfo`) und im Dateikopf (`created_with`).
- **`.github/workflows/release.yml`**, ausgelöst durch einen Tag `v*` (oder von Hand mit
  Probelauf ohne Veröffentlichung):
  - **macOS:** `aarch64` und `x86_64` bauen, mit `lipo` zu einem Universal-Binary vereinen,
    `cargo xtask app` macht daraus das `.app`. Ergebnis: `plnwrk-0.1.0-macos.dmg` (mit
    `hdiutil`), darin App und `plnwrk-cli`.
  - **Windows:** `plnwrk-0.1.0-windows-x86_64.zip` mit `plnwrk.exe` und `plnwrk-cli.exe`.
  - **Linux:** `plnwrk-0.1.0-linux-x86_64.tar.gz` mit `plnwrk`, `plnwrk-cli` und einer
    `.desktop`-Datei.
  - **Veröffentlichen:** Ein letzter Job lädt alles samt `SHA256SUMS` in den Release. Nur
    dieser Job darf schreiben (`contents: write`).
- **Pages:** `pages.yml` baut mit `--public-url /` für die eigene Domain. Die Domain wird in
  den Pages-Einstellungen eingetragen (`gh api`); das ist eine Kontoeinstellung und braucht
  Tobis Zustimmung.
- **Programmsymbol:** Es gibt keins, die App erscheint im Dock als leeres Symbol. Ein
  schlichtes Symbol (Text „p“ auf Hamburger Blau) kommt als `.icns` in das macOS-Bündel und
  als Fenstersymbol in eframe. Das ist klein, aber für eine 0.1.0 sichtbar.

## Global Constraints
- Kein Release ohne grüne Schranke auf dem getaggten Commit (der Release-Ablauf führt
  `cargo xtask ci` nicht erneut aus, verlangt aber einen Tag auf `main`).
- Ein Tag oder Release ist nach außen sichtbar: gesetzt wird er erst nach Tobis ausdrücklichem
  „ja, veröffentlichen“.
- Keine Geheimnisse im Ablauf; `GITHUB_TOKEN` mit minimalen Rechten.

## Review Focus
1. **Pakete auf einem frischen Rechner:** Startet die App nach dem Entpacken ohne Rust?
   macOS Intel und Apple Silicon, Windows ohne Visual C++ Runtime (statisch gelinkt?), Linux
   mit X11 und Wayland.
2. **Der Probelauf von Hand** baut alles, veröffentlicht aber nichts.
3. **Pfade in der Browser-Version** stimmen unter `/` (eigene Domain) wie unter `/<repo>/`.
4. **`created_with` ändert sich:** Alte Dateien öffnen weiter, das Format bleibt Version 2.
5. **Die Kurzanleitung** taugt für jemanden ohne Technikwissen: Jeder Schritt ist sichtbar
   prüfbar.
